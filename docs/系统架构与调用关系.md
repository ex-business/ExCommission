# 系统架构与调用关系

本页是这组代理与佣金工程的统一架构说明，以 ExCommission 为业务主工程。各系统独立运行；运营账号、会员账号、佣金账务和钱包数据分别归属各自系统。

![系统架构总览](images/architecture.svg)

## 1. 每个工程主要做什么

| 工程 | 负责什么 | 不承担什么 |
| --- | --- | --- |
| **ExCommission** | 代理关系、规则配置、来源事实、审批、佣金权益与账本、任务、查询和报表 | 不管理运营或会员密码，不提供管理页面 |
| **ExCommission-Web** | 代理后台、会员代理页面、服务端BFF会话与受控转发 | 浏览器不直接访问数据库、不持有服务密钥、不决定资金结果 |
| **ex-commission-executor** | 独立运行计佣、日结、派发/退款恢复、对账等原后台作业 | 不注册业务管理API，不另写一套计算或账务规则 |
| **ex-ops-identity** | 公共运营账号、认证、站点和角色授权、二次验证与身份审计 | 不替业务系统决定具体资金权限或审批结果 |
| **ex-ops-identity-web** | 运营账号、角色和站点管理界面 | 不融合代理业务页面 |
| **ex-member-sandbox** | 模拟会员注册登录、邀请、充值/投注及退款撤单事实与可靠投递 | 不作为正式会员平台或真实支付来源 |
| **ex-wallet-sandbox** | 独立模拟钱包的派发、原单查询、回执、余额流水与对账 | 不执行真实付款、提现或代理计佣 |

`ex-member-sandbox-identity` 是模拟会员工程的本地目录/身份组件名称，不是新增的第八个业务系统。`ex-commission-worker` 是拆分过程的旧命名，现统一称 `ex-commission-executor`；本轮没有再增加第三个独立“调度系统”。

## 2. 系统架构图

GitHub可直接渲染下面的图。实线表示本次主线的调用或数据协作，虚线表示独立模拟钱包渠道接入的扩展关系。

```mermaid
flowchart TB
    OW[ex-ops-identity-web<br/>运营账号管理] --> OI[ex-ops-identity<br/>运营账号 / 站点 / 角色]
    OI --> OD[(运营身份库)]

    OP[运营人员浏览器] --> WEB[ExCommission-Web<br/>代理后台 / 会员页面 / BFF]
    MP[会员浏览器] --> WEB
    WEB -->|运营登录 / 身份核验| OI
    WEB -->|会员登录 / 会员身份核验| MS[ex-member-sandbox<br/>会员身份与模拟事实来源]
    MS --> MD[(会员与来源事件库)]

    WEB -->|认证业务请求 / CSRF / 站点绑定| API[ExCommission API<br/>业务控制 / 配置 / 审批 / 查询]
    API -->|运营身份复核| OI
    API -->|会员身份复核| MS
    API --> DB[(佣金业务库<br/>事实 / 方案 / 权益 / 账本 / 任务 / 日结)]
    MS -->|验签注册 / 充值投注 / 水位 / 退款撤单| API

    DB -->|读取待处理任务与业务日| EX[ex-commission-executor<br/>独立后台执行进程]
    EX -->|事务 / 租约 / 原单幂等 / 结果| DB
    CORE[ExCommission共享Go模块<br/>规则与事务只有一份实现] -.固定版本构建依赖.-> API
    CORE -.固定版本构建依赖.-> EX

    EX -.渠道适配：派发 / 原单查询 / 对账.-> WA[ex-wallet-sandbox<br/>独立模拟钱包]
    WA -.验签回执.-> API
    WA --> WD[(钱包订单 / 余额 / 流水库)]
    WA -->|钱包运营账号也使用公共身份| OI
```

**当前主线不是 API 通过HTTP调用 executor。** API保存任务和已审批的业务状态，executor从同一业务库领取/扫描待处理工作并提交结果，API再查询展示。两者是独立进程，复用同一套规则模块。执行端只开放健康探针，不开放远程执行或业务管理接口。

## 3. 运营人员操作调用图

```mermaid
sequenceDiagram
    actor U as 运营人员
    participant W as ExCommission-Web/BFF
    participant I as ex-ops-identity
    participant A as ExCommission API
    participant D as 佣金业务库
    participant E as ex-commission-executor
    U->>W: 运营账号登录
    W->>I: 验证账号、站点与角色
    I-->>W: 身份和授权结果
    U->>W: 配置方案 / 提交结算或重试申请
    W->>A: 服务端身份、CSRF、已确认站点
    A->>I: 复核有效身份和站点角色
    A->>D: 业务授权校验、保存申请
    Note over U,D: 需要审批的操作仍由另一位有权限人员审批，本人不能审批自己的申请
    A->>D: 保存已批准状态 / 可执行任务
    E->>D: 读取任务，校验运行状态和水位，取得租约/锁
    E->>D: 复用原事务和幂等键执行并保存结果
    U->>W: 查看进度 / 执行历史 / 报表
    W->>A: 查询本站业务数据
    A->>D: 读取结果
    D-->>A: 本站业务结果
    A-->>W: 授权范围内的响应
    W-->>U: 展示结果
```

运营中心提供身份与角色，ExCommission负责把角色映射成业务权限。业务系统不能把浏览器自报的站点或权限直接当成授权。执行进程沿用 `system-worker` 审计身份，不需要新建运营登录页面，也不绕过审批。

## 4. 会员事实到日结的调用图

```mermaid
sequenceDiagram
    actor M as 会员
    participant S as ex-member-sandbox
    participant A as ExCommission API
    participant D as 佣金业务库
    participant E as ex-commission-executor
    participant W as ExCommission-Web
    M->>S: 通过邀请链接注册
    S->>S: 保存会员及待投递事件
    S->>A: 签名注册事件、邀请凭证
    A->>D: 防重、会员映射、绑定代理关系
    M->>S: 模拟充值 / 投注
    S->>A: 签名业务事实，携带原业务单号与实际业务时间
    A->>D: 防重、匹配已启动方案、更新资格及相关奖励
    S->>A: 签名业务日水位：事实数量与摘要
    A->>D: 核对实际事实，保存完整水位
    E->>D: 到期检查方案状态、水位与任务幂等
    E->>D: 冻结依据、日结计算、生成待审核权益
    Note over E,D: 未启动/停止方案禁止新结算；原权益与历史继续保留
    M->>W: 查看奖励和佣金进度
    W->>A: 会员本人查询
    A->>D: 读取本人权益与历史
    D-->>A: 本人权益与历史
    A-->>W: 会员响应
    W-->>M: 展示本人结果
```

事实接入、资格刷新等部分处理仍可能在 API 业务事务中完成；拆分不是把所有业务函数都远程化。异步计佣、日结及恢复由独立执行进程承载。方案、生效时间、币种、账务与冲正仍执行各自已实现的规则。

## 5. 领取、派发与钱包边界

当前已验证的会员领取链路是在 ExCommission 自身业务事务中更新权益、账本及本地钱包记录。独立 `ex-wallet-sandbox` 已有自己的模拟系统与适配分支，但它的渠道适配尚未并入本次共享基线；不能把所有会员领取都描述为已经调用了外部钱包。

外部钱包渠道接入后的目标调用如下：

```mermaid
sequenceDiagram
    participant A as ExCommission API
    participant D as 佣金业务库
    participant E as ex-commission-executor
    participant W as ex-wallet-sandbox/正式钱包
    A->>D: 保存已审批、可派发的原单
    E->>D: 领取待处理派发，锁定原单
    E->>W: 签名派发，沿用唯一商户单号
    W->>W: 原单防重、记余额及流水
    W-->>E: 明确成功 / 失败 / 结果未知
    W-->>A: 签名回执
    A->>D: 验签、站点绑定、防重后更新结果
    E->>W: 结果未知时查询原单，不另造新单
    E->>D: 对账、保存差异与恢复依据
```

该图表示渠道协议分工，具体业务调用可能在API首次派发时立即发生，executor负责后台恢复与对账；不会为了图示而重写现有付款状态规则。充值退款、投注撤单由来源发送关联原事件的冲正事实；未领权益调整，已领权益保留追偿，不自动扣外部钱包。

## 6. 数据与部署边界

| 数据 | 归属 |
| --- | --- |
| 运营密码、角色、站点授权、身份会话 | ex-ops-identity自己的数据库 |
| 会员密码、会员登录、模拟来源事件及投递记录 | ex-member-sandbox自己的数据库 |
| 代理关系、方案、业务事实、权益账本、审批、任务、日结、追偿 | ExCommission业务数据库，API与executor共享 |
| 独立钱包的订单、余额、流水、回执队列 | ex-wallet-sandbox自己的数据库 |
| 浏览器会话与上游凭据 | 各Web/BFF的服务端边界；不暴露服务密钥给浏览器 |

独立executor不表示拆出第二份佣金数据库，也不表示新增另一套计佣算法。API、executor需要使用兼容的共享模块版本和相同的作用域/渠道配置；多站部署仍按既有单作用域worker配置安排实例。
