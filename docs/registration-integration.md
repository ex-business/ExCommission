# 注册与首次邀请归属接入

本次范围：佣金系统接入能力。未接任何真实会员注册服务，未实现会员注册页面，也不处理密码、验证码、充值达标、等级资格或发奖。

## 扩展边界

`registration/application` 编排事务，依赖 `registration/ports`：Source 验证可信注册事实，Users 写用户身份，Agents 建立代理及首次关系，Repository 保存邀请与注册凭证。用户和代理表仍分别由各自模块的适配器维护。增加 HTTP、消息队列、站点来源时，装配新的 Source 和入口，不复制注册规则或把会员数据库耦合进佣金系统。

来源适配器只能提交已经注册成功的事实。当前只有本地 HMAC 沙箱，双重校验既有后台权限和来源签名；真实服务需要单独的服务主体授权及来源配置，不能使用本地操作员令牌上线。未修改公共鉴权、站点识别或响应代码。

## 本地配置

运行 `python3 tools/init_local.py` 生成独立 `LOCAL_REGISTRATION_KEY`，不打印密钥。在本地私有 `.env` 明确设置 `LOCAL_REGISTRATION_ENABLED=true` 后重启 API；默认关闭，原有同步和手动代理流程不变。

`LOCAL_REGISTRATION_URL` 可设置为后续实际会员注册页完整 URL。邀请接口保留已有查询参数并加入 `ic`。未配置时 `registration_url=null`，仅返回邀请码；这不表示已经有可用的会员注册页面。URL 由服务端配置，调用方不能在请求中指定跳转目标。Docker Compose 已透传上述配置。

## 接口

所有写请求沿用现有 Bearer 鉴权、`Idempotency-Key` 和响应信封；契约在 `contracts/v1/openapi.json`。

1. `POST /v1/registrations`：接收已完成的注册事实，要求 `users:sync`，并要求 `X-Registration-Signature`。
2. `POST /v1/registration-invitations`：`{"source_id":"sandbox","agent_id":"已有代理编号"}`，要求 `agents:write`。返回不可猜测的邀请码、来源、邀请人、创建时间及可选注册页链接。

无邀请注册事件示例（时间换成真实注册完成时间，不得晚于服务端当前时间，精确到微秒）：

```json
{
  "schema_version": "1",
  "source_id": "sandbox",
  "event_id": "registration-unique-event",
  "external_user_id": "member-external-id",
  "display_name": "会员名称",
  "registered_at": "2026-10-16T10:00:00Z",
  "invitation_code": null
}
```

邀请注册时，将 `invitation_code` 替换为注册页 `ic`，由注册服务绑定注册事件后提交。不要允许会员客户端自行调用受控接入接口。浏览器不持有来源密钥。

签名输入是下面前缀的 UTF-8 字节加原始 HTTP JSON 字节，使用独立密钥做 HMAC-SHA256，结果转十六进制。所有换行都是 LF，前缀结尾也有一个 LF：

```text
registration-v1\n{tenant_id}\n{app_id}\n{source_id}\n
```

作用域来自已认证主体及服务端装配，不接受请求体指定租户/应用。签名前后不能重新序列化 JSON。新增来源须在服务端显式注册，单独配置凭据；更换 source_id 不会自动成为可信来源。

## 业务不变量

- 用户映射、代理账户、ACTIVE 历史、首次父关系、注册凭证、事件去重和 `registration.completed.v1` outbox 在同一事务提交；失败整体回滚。新代理不自动获得任何方案的等级或计佣资格。
- 无邀请注册得到根代理。有邀请时校验邀请码的租户、应用、来源，以及邀请人当前和注册时点均 ACTIVE；注册时间不得早于邀请码创建时间。无效邀请返回明确失败，不静默降级为无上级。
- 外部用户唯一键为 `(tenant, app, source, external_user_id)`。同一注册事实更换事件号/幂等键重投返回原代理；保存每个事件别名，事件号不可转给其他用户。
- 注册首次归属不可覆盖。即使首次无邀请，后续补邀请码也拒绝；改变注册时间或显示名同样属于事实冲突。姓名更新继续走用户同步，关系变更继续走原独立审批。
- 已经手动创建代理的历史用户不通过注册接口补绑，返回冲突；本次没有批量回填历史用户或将普通同步用户自动转代理。
- 注册与原关系迁移共用作用域锁，防并发成环。当前按租户/应用串行，是正确性优先的基线；没有做吞吐容量验证，未来可按关系分片演进。
- 当前 outbox 只接现有本地审计和通知投递；没有声称真实 Kafka/注册服务已经联通。后续消费者必须按事件号幂等，不能让后置消息替代核心注册事务。

## 其他业务影响与验证边界

【涉及其他业务】未来会员注册链路：注册服务提交成功事实 → 注册接入 → 用户身份与代理关系 → 后续计佣历史查询。邀请链接归属应在真实注册事务/可靠 outbox 中固定，网络超时保留原事件号重试；注册服务不应因为重复投递修改上级。实际注册服务及其登录、钱包、充值、游戏流水未改、未联调。

默认关闭的新入口不改变原同步、手工创建代理、关系审批或计佣资格。新增数据库迁移 `016_registration.sql` 仅创建三张注册业务表；不修改历史迁移和已有表。停用接入开关即可停止新流量，保留已创建的历史关系和审计，不能用删表撤销业务历史。
