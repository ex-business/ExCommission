## 冲突取舍与冻结规则

1. 详细后台配置页优先于早期「代理规则」概述：等级人数统计仅直属一级；等级日有效投注含下线三层所有邀请会员，不以有效会员资格筛除。物理层级固定三层，关闭或不合格节点不压缩层级。
2. 推荐阶梯人数是本阶梯新增人数：配置 1、3、8 时，累计 1、4、12 人分别解锁；1人不能同时用于多个阶梯。依据配置页「再推荐3人」及会员页4.6人数求和。每阶梯一生领取一次，不按日重置。重复人数配置拒绝。
3. 等级、推荐、受邀各自使用独立的充值与有效投注阈值，全部为正，且两项同时达标；资格累计不因自然周期清零。等级人数按首次达标时间落入配置周期（日/周一至周日/月/永久），周期创建后不可改变。
4. 注册即具有推广身份，后台代理总表只展示至少有一名直属下级者。邀请归属在可信注册事件中一次绑定，不能通过已注册后的邀请链接抢绑。
5. 受邀奖励归受邀会员本人，一生一次；仅邀请注册者拥有该栏。推荐奖励归直属推荐人。三类奖励手动领取至真金钱包，无额外流水。每个阶梯/每日佣金/受邀奖励均生成独立交易和账变。
6. 等级按业务日结束后的最终人数与三层有效投注同时判定；未达更高等级使用Lv0。当日所有有效投注按同一最终等级的对应物理层比例计佣，不按投注当时等级。金额为最小货币单位字符串，比例为整数PPM（100%=1000000），按代理、层级汇总后向下取整；禁止浮点。跨层总和不提前取整。层内会员贡献采用最大余数分配（余数相同按用户ID），确保明细之和严格等于层佣金，避免分笔取整造成少发。
7. 使用站点IANA时区划分自然日/周/月，明确配置。原型未指定时区，默认UTC延续现有契约。次日当地01:00处理昨日；夏令时重复时刻按业务日期去重，不存在的01:00取该日首个到达01点之后的时刻。关账后迟到事实须独立调整，不能静默改已审核金额。
8. 参与游戏类型使用可信场馆类型目录（体育/电竞/真人/彩票/棋牌/电子/捕鱼等），不把交易产品代码作为场馆类型。充值、提款仅成功订单，投注仅已结算订单；数据源必须验签与幂等，不能由会员自报。
9. 业务佣金审核「通过」原子产生待领取状态，「取消」不允许领取；调整金额至少1个主货币单位（例如2位精度币种最小100），可大于原始计算额但须记录差异、审核人、时间与备注。已有资金守恒、独立审批及权限约束继续生效。
10. 单代理关闭与站点关闭分开。单代理关闭仍展示入口，三类奖励停止新增且既有未领取不可领；重新开启从新开启时间起统计，关闭区间不追补。操作需二次确认和TOTP；接口本身也强制验证。
11. 查询时间区间左闭右开，最大一年；默认值依原型页面（总表今日、下线昨日、审核昨日、受邀近7日、会员收益近24小时）。必须同时支持当前页和全条件汇总、稳定分页、敏感IP权限。
12. 实时奖励展示只用真实已领取且脱敏记录；原型「早期造假数据」不作为实现要求。分享仅准备链接与内容，由用户在社媒确认发布。站点、用户身份、权限不可来自可伪造的会员请求参数。

13. 原型早期示例把C3同时画作B2直属、又计入B1佣金，且C1示例等级与公式不一致。验收以真实直属关系及配置的等级公式计算：固定图中B1的直属只有C1/C2，不额外加入C3；不复制错误示例金额。

## 完成判定

每项需给出代码、真实数据/事务测试、接口契约和适当浏览器证据。模块实现、远程推送、正在运行的版本、生产外部钱包/订单源接入分别验收；任何一项没有证据不可标全部满足。Docker管理接口此前500不意味着可以免除最终部署核验。
