# 会员代理业务顺序实施与验收

顺序固定，逐项完成契约、实现、测试和中文提交：

1. 会员手动领取进入真金钱包，关联交易历史与账变记录（已实现，验收通过）。
2. 代理总表及三层下线明细、业务统计、VIP与登录IP、分页及汇总（已实现，验收通过）。
3. 站点代理方案绑定、功能开关与参与场馆（已实现，验收通过）。
4. 代理开关停止三类奖励与领取、谷歌验证（已实现，验收通过）。
5. 会员PC/H5推荐奖励、团队、收益、规则与分享二维码（待实施）。

## 第一项：真金钱包契约

项目新增独立 wallet 模块，管理真实货币可用余额、不可变交易历史和账变。它与佣金权益账本分离；钱包的 REAL_MONEY 类型是可用货币余额，不是可提现的外部银行到账证明。第三方已有钱包应通过模块端口接入，禁止用沙箱成功冒充外部钱包到账。

新增 wallet 付款通道。会员领取继续复用现有接口，后台在发布领取单时指定 wallet。受信内部通道返回入账指令，付款成功处理在同一 MySQL 事务内完成：锁定结算与预留权益 → 锁定本人币种钱包 → 增加可用余额 → 生成交易历史及账变（前后余额、金额、付款ID、结算ID）→ 预留佣金转已付 → 付款确认成功。任一步失败全部回滚。

钱包受益人从已审核结算对应代理的内部 user_id 获取，不接受客户端提供收款人。merchant_payment_id 作为唯一业务引用，并发和重复核验均只入账一次。SUBMITTED中断后由原付款核验恢复；wallet不接收外部回调，不能用伪造成功回调入账。金额使用最多38位正整数最小货币单位，余额溢出拒绝。

新增 GET /v1/me/wallets、GET /v1/me/wallet-transactions、GET /v1/me/wallet-changes。本人权限和可信身份沿用上一项，分页及币种过滤，不向会员暴露其他用户。交易和账变不允许修改删除。

验收必须证明真实数据库钱包余额、交易、账变与佣金已付金额一致，重复/并发不重复入账，失败原子回滚，跨会员隔离，恢复原付款成功，沙箱流程不受影响。

第一项验收：真实MySQL会员领取通过；注入钱包入账后异常，钱包余额、交易、账变与佣金账本整体回滚。原付款恢复后仅入账5000最小单位，重复核验和并发关联不重复入账，另一会员读不到钱包记录；wallet回调被拒绝。

## 第二项：代理总表与三层下线契约

GET /v1/agent-directory 返回代理总表；GET /v1/agents/{id}/team 返回指定代理一至三层下线；GET /v1/me/team 返回本人团队。成员包含代理关系中的下级代理和用户绑定中的普通会员，普通会员不人为创建代理账号。深度按真实关系计算，不压缩层级；层级范围1..3，可筛选某一层。采用关系历史有效区间，统一as_of快照和user_id游标；每页1..100。

业务数据由可信来源推送累计快照 POST /v1/member-statistics。快照包含内部user_id、currency、observed_at、deposit_minor、withdrawal_minor、bet_minor、valid_bet_minor、VIP及最后登录IP。四项金额为非负、最多38位整数最小单位；IP校验规范化；只有有权来源的原始字节HMAC签名通过才接收。相同时点重放一致返回原结果，改变已有事实冲突；不修改历史。

列表按指定币种读取as_of之前最新快照，返回数据时点。未知统计返回null而非伪造0；缺失会员计入missing_statistics。汇总覆盖全部匹配人员，和当前分页独立，币种不混加；只有完整数据时汇总才标记complete。数据为截至时点累计值，不冒充指定日期段发生额。

新增agents:directory和users:statistics写入权限。登录IP另需agents:sensitive:read，会员团队接口始终不返回下线IP，后台无敏感权限时返回null。统计接口不接受外部自报租户，内部用户须存在，统计、关系查询及汇总均有租户/应用隔离。

第二项验收通过：五级代理链只返回前三层，并包含普通绑定会员；统计快照重放一致、修改历史冲突；分页汇总保持四人合计700；缺失数据、VIP、规范化IP、后台敏感权限和会员IP隐藏均通过真实MySQL/HTTP验证。18份响应与6份请求契约通过，前端查询、筛选及分页浏览器场景通过。

## 第三项：站点代理配置契约

站点使用已有tenant_id/app_id作用域，一个app对应一个站点，不引入可自报的跨站点ID。站点配置包含enabled、绑定已发布plan_id、参与venue_ids；场馆ID与已接入来源的product_code使用同一契约值。佣金选取绑定方案在business_time生效的版本，并核对路由；达标奖励沿用各已审核活动的奖励方案，不把活动方案替换成佣金方案。

配置采用申请/独立审批、expected_revision、不可变版本历史；审批执行时立即生效。GET /v1/site-agent-config 和 GET /v1/site-agent-options；POST /v1/site-agent-config-requests，审批沿用通用审批接口。初次未配置保持旧通用模式，响应明确configured=false；一旦配置，不回退绕过绑定和场馆约束。

关闭后阻止新佣金事件、达标奖励观察/触发、新计算入账、领取及创建付款。已有快照也在提交前重验开关；已发生的付款结果继续核验，不能因关闭丢弃真实到账事实。冻结和退款纠正保留，不删除原权益。配置的历史开关和场馆选择按业务时点校验；当前关闭仍阻止执行。

第四项将在此流程增加谷歌验证，保持独立审批，避免将验证码写入命令、日志或公开仓库。

第三项验收通过：独立审批、版本竞争、场馆拒绝、关闭前已保存快照在提交前拦截、关闭期间新事件/达标奖励/领取拒绝、重新开启后人工恢复原任务；共享门闩保证关停与业务提交串行。117份响应及43份请求契约、受影响Go竞态回归、前端14项测试及配置浏览器场景通过。

## 第四项：代理开关与谷歌验证契约

奖励开关沿用上一项的全链路门闩，覆盖事件佣金及两类由达标活动表达的固定奖励；活动仍分别配置独立条件和一次性发放约束。关闭不冲销既有权益，领取与新派发禁止，已提交渠道的真实结果仍须核验。

站点配置申请、批准生效、失败执行恢复均强制TOTP。每位管理员使用独立种子，绑定tenant/app/subject；独立审批和TOTP互不替代。验证码通过X-TOTP-Code传递，正文、幂等键、数据库命令和日志均不包含验证码。采用RFC6238、SHA1、30秒、6位、前后各一个时间步；参考 https://www.rfc-editor.org/rfc/rfc6238 。

校验状态使用持久化单调时间计数器：同一验证码只允许同一动作、同一幂等键和相同正文重试，跨动作或新键重用拒绝；服务器时钟倒退也不能恢复旧验证码。每位管理员每分钟最多五次校验，失败次数独立提交，不随业务事务失败回滚。无配置、无验证码、无权限或存储异常均不绕过。

执行 python3 tools/init_totp.py 为本地两个管理员生成独立配置，不覆盖既有种子，不打印种子。0600权限的.local/totp-accounts.json含provisioning_uri，需各管理员本人绑定Google Authenticator或兼容验证器。Docker通过受保护的.local/totp.env注入，非root运行无需将种子文件放宽权限；文件与环境都不上传Git。初始化配置不代表管理员已在手机绑定。

第四项验收通过：RFC六组向量、有效时间窗、缺失和错误验证码、动作与幂等绑定、防重放、时钟回退、持久化限流、敏感配置权限及真实配置审批测试通过；受影响运行时与审批恢复竞态回归、前端15项和验证码头部浏览器验证通过。本地种子已初始化但未代替管理员完成手机绑定。
